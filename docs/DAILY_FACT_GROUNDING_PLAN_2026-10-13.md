# 10 月 13 日 Meta 错配：调查与最小修复计划

## 目标与边界

先确认补图与 Meta 更正仍在线，再追溯原始缓存、提示词输入、生成和校验。保护原目录的分叉和用户改动，在 D 盘独立 worktree 工作。不改 UI、商机、定时、模型线路或 8192 输出预算，不给全部新闻增加第二轮模型审稿。

## 已确认的链路

`数据源 → KV 原始缓存 → dailyPromptSelection 的 Content Summary → buildDailyGenerationPromptInput → 正文模型 → 格式/结构校验 → 可选媒体后处理 → 发布`。

生成时不会因正文附有链接就自动读取链接文章。新补图流程在成稿校验之后，不能追溯为正文生成提供依据。publishValidation 当前不接收原始素材，所以不能判断产品类别是否与原文相反。

## 待验证的假设

1. 缓存只有标题、原链接和 HN 讨论数字，没有文章内容，模型在强制扩写时猜测了类别。
2. 聚合源拆分错误，标题/链接与其他条目正文混配。
3. 输入正确但生成模型错误联想；原有真实性规则未被遵循。

区分已证实事实与推断，不把模型内部联想冒充可观测日志。保存当天缓存和实际提示词作为复现证据。网络受限时用仓库现有只读检查 workflow，不触发正式生成或改写 KV。

## 最小实施顺序

1. 只读检查 workflow 留存公开缓存，回放候选构造，定位原词首次出现的位置。
2. 针对实际缺口补测试，再改最小责任模块。优先修复采集正文缺失与每条事实边界；不靠全局拒绝发布、硬编码某产品或关键词黑名单。
3. 如果某类候选确实只有讨论元数据，限量获取该篇真实标题/正文摘录，并明确标记材料来源与不足。原文无法取到时只能使用原题明示信息或更换其他候选，禁止从产品名猜能力。
4. 保留现有完整来源和长文正文，避免新摘要覆盖好素材。所有额外请求有数量、超时与响应大小上限，单站失败不拖住整篇日报。
5. 生成提示词只增加简短、针对性约束：标题不等于正文；讨论热度不是能力证据；不得从名称猜类别或补状态。
6. 运行回归测试与最终代码完整 dry-run，逐条核对 Meta 和其他只有标题的条目。不覆盖已修好的线上文章。通过后按原 SSH 与 Worker 部署流程发布代码。

## 验收

- 固定的错误输入能复现原提示词缺口，修复后原文的智能体类别与关键事实进入实际模型输入。
- 没有原文时不会把 HN 点赞/评论当作产品功能证据。
- 完整预览有真实来源支撑，不再出现音乐生成误写；图片、趣闻和 FAQ 不回归。
- 原定时、其他栏目和发布失败边界不变；记录额外网络/token 消耗及未能覆盖的风险。

## 已查明的原因

只读检查运行：https://github.com/dongyu19920904/CloudFlare-AI-Insight-Daily/actions/runs/38343007419 。已保存公开缓存副本 `artifacts/source-evidence/payload.json`。

原始条目来自 Folo feed `41440449356332047`，来源 `Hacker News: Best - meetpateltech`，标题只有 `Muse Wonder`。content_html 与 description 都只有 Article URL、HN Comments URL、Points: 492、# Comments: 266，没有产品类别或功能正文。

回放旧版真实候选构造后，模型输入仍然只有这些内容，未读取 Meta 原文。原始数据及生成前字符串都没有“音乐生成”，错误首次在模型输出成稿出现。没有证据表明这条发生了跨新闻拼接；模型是否联想到旧音乐模型属于推断，无法由日志证明。

责任分为三层：采集把“讨论条目”交给了成稿链路；候选构造把讨论元数据命名成 Content Summary；生成要求每条形成完整段落，而真实性规则没有足够的原文支撑。格式校验不接收原文，无法发现类别错误。末尾的“具体能力以官方博客为准”也不能抵消前面已经写出的错误类别。

这不是 CSS、补图或翻译导致的。上一轮 before.md 已保存改图前的同样错误；补图流程只在校验后运行。上一轮修好了已发布的单条错误，本轮才是在修未来生成时的上游缺口。

## 已实施的最小修复

- dailyNewsGrounding.js 只识别完整 HN 讨论元数据模板，已有正文的素材不触发。优先给原先选中的条目读取精确原链接的标题和文章段落；只有页面 description 时明确标记为部分材料。
- 不读取推荐区、导航或页脚填事实，不用另一篇页面替代原链接。原始缓存保留讨论信息；成稿输入的 Discovery Metadata 只保留讨论来源标记，不再传入点赞、评论数字。
- 每次最多 6 篇、10 次 HTTP（包含重定向）、3 并发、12 秒总时限、4 秒单请求、512KB 页面上限；没有第二轮模型事实审稿，也不新增线上配置变量。
- 取不到原文的空壳候选退出本次新闻池，重新运行原来的选择器，从其他完整素材补位。不会新增整篇拒绝发布门槛。原始 KV 缓存不被改写，其他栏目未开启该步骤。
- dailyPromptSelection.js 保留真实 Original Article Title、正文摘录与材料范围；另修正原有 content_html 为空时丢失 description 的问题，以及图片 URL 占满 500 字摘要、真实正文被截断的问题。媒体仍保存在独立 Media References 中，原缓存摘要上限保持 500；仅新抓取的原文摘录上限为 1600，避免英文发布开场白挤掉接入与限制条件。
- 主提示词只新增一条针对性约束，禁止从陌生名字猜类别、把讨论热度当能力证据、把相邻新闻能力移入本条。
- 固定复现测试先失败，随后通过；最终完整 Node 回归 467/467 通过，包括商机隔离、主日报结构与配图测试。前端未改代码，现有 22/22 测试复核通过。

## 实际生成与纠偏

完整分支 dry-run 使用当天缓存、生产固定设置与相同 scheduled 生成函数，拦截所有非模型写请求，KV 写入直接报错，因此不会覆盖线上日报或修改生产缓存。没有把单元测试当实际成稿验收。

第一次完整预览 38343976958 的 Meta 类别已正确，但模型仍写了未经支持的“热度超过同期多数发布”，并将另一条 HN 评论数字改错。因此未上线该版本；删除成稿输入中的讨论数字，而不是再增加一个模型审稿器。

第二次完整预览 38344370863 不再泄漏 HN 数字，Meta 正确写为个人与专业智能体。继续检查实际模型输入时发现长图片 URL 抢占正文摘要，遂增加媒体/事实字段隔离并运行最终预览。

第三次预览 38344595548 显示机器人条目已拿到原文的 56.9% 与 72.7% 数据，不再仅凭图片后的副标题猜写；同时发现模型会自行把 Skill 升级成 MCP、将玩笑写成真实公司组织事实。只增加两条简短文案约束，并补齐新原文摘录里的接入条件，不新增模型校验调用。

第四次预览 38345063126 的类别与核心能力正确，且拿到了完整的开放条件；人工检查发现“Wonder 和 Full 共同通过 API 开放”与后一条“Full 仅限 Muse Code 订阅者”存在表达冲突，以及将原文 today 误写为日报当天。进一步加入逐版本对应权限、不要把原文 today 移成日报当天的短规则。没有将该测试稿发布，也没有声称通过结构校验等于事实完全正确。

只读源核对实际请求 6 次，4 篇获得原文摘录或页面 description；GLM 动态脚本壳和超大 GitHub issue 页面没有当作有效正文，使用其他完整候选补位。完整预览保留 TOP 10、开源、社媒、趣闻、来源配图与带有效主站链接的相关问题。

曾发现本地预览脚本遗漏入口的固定默认配置，已取消那次测试并修正脚本；未影响生产。以后本地分支预览也使用 withWorkerConfigDefaults，保持 8192 正文预算与原来源选择设置。

## 风险与不做的事

不能把一次修复说成“所有未来新闻零幻觉”。本轮降低的是已证实的“仅标题/元数据硬扩写”风险；来源本身写错、模型不遵守正文约束和未抓到的动态页面仍需分别处理。

不把来源可信度等同于完整正文，不因 URL 是官方域名就假定模型已经读过。不增加大量关键词黑名单、产品特例、第三方浏览器依赖或无限重试。最终发布代码前仍须检查真实完整预览；不覆盖今天已经修正的线上好内容。
