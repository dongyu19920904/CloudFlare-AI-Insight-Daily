## 已核实的问题

1. dailyMediaCoverage.js 的全局默认目标为 6，社媒额外照顾 2 条，但开源和趣闻没有独立保障；达到目标后其他带图文章不再补图。
2. 采集候选只提取 details.content_html 内 img src / video src，没有从文章正文补取媒体。今天 Ars、Meta、GLM-Legal、mortoray 的缓存只有 HN 链接、分数和评论数，没有图。
3. bestblogs 摘要长达 8364 字符，但缓存无 img；不能把摘要有字等同于原文媒体已采集。
4. GitHub daily trending 只存 owner、语言、星标等元数据，没有 README 图片字段。Open WebUI README 的首批是徽章，真正展示图为 ./demo.png；BitNet 对应 ./assets/performance.png。不能机械取第一个图片。
5. 趣闻源 dotey/2109737617184936351 缓存已有引用帖的 pbs.twimg.com/media/HUa4gztbcAAhp_y 图片；它不是没有采到，而是独立趣闻晚于补图步骤插入，末尾没有再补图。
6. Telegram shiji-kb 缓存含 telesco.pe 图。它被有意禁止长期热链，另有最多 4 张/500KB 的归档；归档失败时不补，不能用不相关图片替代。
7. 原目录的 Hugo render-image 能正常输出 figure/图注，缺图首先发生在 Markdown，不是调颜色能解决。

## 独立发现

Meta 官方 Muse Wonder 页面描述的是 personal/professional AI agents，不是日报写的音乐生成。补图不能证明原文没有的说法。本轮记录事实问题，不悄悄重写整篇；涉及该条图片必须明确来源，避免用音乐素材填充。

## 解决方案

在完整成稿（包括独立趣闻）已经通过校验后，增加一次可选、确定性的媒体补全，不再调用模型：

- 只处理正文已引用、缺媒体的新闻/开源/社媒/趣闻块，跳过 FAQ，原文字和已有正确媒体不动。
- 优先使用已缓存且归属于同一 URL 的真实媒体。这样推特引用图直接复用，不额外抓 X 或依赖新代理。
- GitHub 读取确切仓库 README，解析相对图、HTML img/picture、Markdown 图；跳过徽章、头像、状态图、赞助广告，选择最前面的有效展示图。
- 普通文章只读取精确原链接，优先正文图或该篇 OG/Twitter 封面，处理 lazy src/srcset/video poster。不得扫描相关推荐或用全站默认分享图凑数。
- 每条最多补一张；复用现有覆盖函数，但此次目标按真实可用来源计算，不因为前六张已经存在而跳过趣闻和开源。
- Telegram 继续现有有界归档，不开放失效热链。
- 限制文章/README 请求数量、并发、超时、响应大小，图片验证状态/类型；只有公共 HTTPS URL，不访问内网，不携带凭据到外站，不绕过反爬/登录。
- 整体补图超时/单站失败只跳过图片，主体日报照常发布。日志逐条记录来源、结果及没有补上的原因。

## 剩余限制与成本

自动配图明显改善，但不能承诺所有原站每次都可抓：客户端渲染、反爬、登录限制、临时 CDN、权限与第三方图片代理均可能影响。只跳过对应图片，不借用其他新闻的图片。
新增媒体是原文图/原文封面，不等同于原媒体授权再分发；保留来源，尊重原站版权和热链约束。
新增代价是有界网络请求与最长 20 秒可选后处理，不增加 AI token、定时任务或付费浏览器；也不新增存储服务。原定时、模型、预算、正文样式全部未变。
