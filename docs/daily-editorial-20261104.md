## 检查结论

1. `dailyPromptSelection.js` 普通图片素材额外加 24 分；大厂优先只覆盖 `dailyGenerationPromptInput.js` 中少数固定模型名称、发布动作和官方 URL，普通功能更新没有同等优先逻辑。V2EX 的来源栏目名恰叫 OpenAI，也会误占 OpenAI 实体限额。
2. `dataFetchers.js` 先按有无图片排序，再由 `newsSourceDiversity.js` 留大部分原排序记录到固定 50 条。多张广告和日常社交图片可挤掉没有图片的重要更新。修复保留相同抓取与缓存上限，只改善截断前的次序。
3. `dailyGenerationPromptInput.js` 要求十个候选必须逐条使用、不能丢弃；与系统提示的弱素材应跳过冲突。模型于是把不适合成新闻的候选写成“素材缺乏可核实内容”，把未证实的传闻写成自行判假的报道。
4. 原文 36 氪是带演示的传闻文章，并不能支持日报擅自断言“属标题党”或“官方目前没有发布”。没有足够事实时可不用它，不凭模型常识判断真伪。
5. `getDailyPublisherKey` 对 X 取账号、对即刻取署名；归藏跨平台被当作两个发布者，独立补入社媒的候选又只查 URL/少数事件键，重复逃过分区检查。向阳乔木与归藏也没有合计限额。
   - 复验还发现 Telegram 26595 原封转载归藏提示词但未署名。两位作者的原帖在池内时，使用至少 80 个规范化文字的正文前缀识别其同文转载，避免换成 Telegram 就绕过合计限额；普通社媒同文转载也用该指纹辅助去重。
6. 原图 AIBase 的两张图片均已在缓存里。全局原图补齐默认目标为 6 张，并不等于每条有原图的新闻都会获得原图；后续联网补图仍可能受预算/网络影响。对已知对应关系在本地回填，不增加抓取请求。
7. “AI 第一个受害者”原图是涉及个人和公司的严重指控截图，真实性未核实，不适合作为轻松趣闻传播。本轮删除该候选；仅有图和一句标题的素材不让文本模型猜图编故事。
8. 这份 Folo 数据没有可靠的点赞数。不能把“缺失热度”伪装成低热度，也不能说程序已经知道某帖只有一赞；用时效、事件影响、是否具体更新及内容完整度降低老旧自荐占据前排的概率。
9. Linux.do 的 Folo ID `100023840905641984` 仍配置在列表中，今天缓存可见该源“现在新人写手推荐哪个平台？”；并非取消订阅。旧 `applyLinuxDoPolicy` 在编辑筛选前按输入顺序只保留两条，且历史防盗链规则去掉 HTML 图片，后续媒体优先排序又使它偏后。另一个 Linux.do 源 `90750267735802880` 是“福利羊毛”，复验可见它的 Gemini 抽奖；不能把长篇抽奖规则当高质量新闻。保留两条上限和防盗链，只在截断前比较实际更新、正文完整度、AI 相关性，降低求推荐和抽奖帖占满名额的风险。源未必每天有合适新闻，不强行塞进 TOP，也不承诺本次一定有入选。

## 修改顺序

1. 增加纯本地的编辑信号小函数：识别真实产品更新/重大事件、标题式素材、传闻、内容自荐，提供排序信号；不替模型裁定事实真伪。
2. 固定新闻缓存截断前优先保留真实大厂更新与完整新闻，维持原有 50 条和发布者多样性预算。
3. 候选排序降低“有图即重要”的权重；大厂真实产品更新优先，来源栏目名不冒充公司实体。向阳乔木/vista8 和归藏/歸藏/op7418 跨平台合计每日最多一条，含趣闻备用池。
   - 首轮实际预览仍把 AIBase 聚合稿拆成两条，未发布。对明确编号的 AI 日报聚合稿，在进模型前只保留第一条完整事件及其对应图片，不把相邻事件/配图混成一个候选。
4. 在候选分区和补位中继续复用该限额/去重结果；重要更新不被机械预留给末尾社媒。用同池其他候选替换不够成稿的条目，不写核验说明或自行辟谣凑数。保留 TOP10 和已有替换机制。
5. 两处现有原图回填调用对每条已匹配来源进行补图，不改定时路由、不增加联网和模型调用阶段。
6. 增加针对以上问题的单元测试，跑全量后端测试。从最终分支完整 dry-run 今天日报，逐条审读事实、重复、原图、趣闻、FAQ；预览不通过先修复，不覆盖线上。
   - 再验暴露三个边界：HN 的链接/点数元数据不是正文，不能作为“有摘要”依据；无描述的项目不能仅凭仓库名猜用途；已有更强的真实反差实验时，趣闻不应因为普通工具恰在主候选外就选普通工具。分别本地去掉元数据、排除无描述项目、为复古硬件跑现代 AI 的反差保留趣闻名额；不新增模型阶段。写稿按已排好的 TOP 候选顺序，不让末位体验帖再次升为第一。
   - 原缓存已经截断，不能反证截断之前是否有重要新闻。只读重采集因 Folo 凭据不在 KV 而无法使用，已撤回该实验。复用现有预览工作流的 refresh_sources 开关，调用现有 Worker 的 testFetchCategory 仅刷新 news 缓存，再读取缓存运行分支预览；不导出 Folo 凭据、不写文章。生产仍是旧截断逻辑，新增排序在完整原始素材上的效果以回归测试证明，不冒充已经线上重采集验证。该开关默认关闭，不改变自动生成流程。
   - 第二轮程序通过但成稿不合格：把“Token 自由”扩成“全部免费”，并漏掉社媒。进一步验证使用 `wrangler versions upload` 的版本 URL：不切换生产、不改 cron，只在该版本调用原有 news 抓取入口，以同一组绑定验证新截断；版本 URL 仍共享生产资源，故仅允许已说明的当天 news 缓存更新，不调用正式发布入口。预览参数默认关闭。
7. 通过后按原流程部署 Worker；今日成稿只有明确优于现版、经过核对才发布。前端只更新对应 Markdown，不改样式，构建并检查首页/日期页。

## 验收与回滚

- TOP10 不含“缺乏内容”“无法提取事实”等内部审稿结果，不自行断言传闻为假；替代条目必须来自真实候选。
- 已有重要大厂更新优先于普通工具/自荐；没有真实更新时不编造某厂当天发布。
- 两位作者合计最多一条，不重复同一跨平台帖子/配图；其它作者仍维持原有多样性规则。
- AIBase 资讯配图来自该篇原文，原图补齐不取无关推荐图。
- cron、模型、API、时间窗、其它栏目的代码和 UI 不变；没有新增阻塞发布的校验。
- 复验额外发现稳定性缺陷：两次完整初稿通过发布校验后，仅因可选润色请求 ECONNRESET 导致整篇中止。只在已有完整初稿通过既有校验时隔离润色异常并保留原稿；初稿不合格仍抛错，不放松门槛、不生成兜底文字、不改变触发时间。增加两项真实分支测试。
- 记录测试、完整预览及部署回执，明确自动验证和人工核对的区别。回滚只 revert 本轮代码提交与本次日期稿件提交，不 reset 原目录或丢弃别人的修改。
